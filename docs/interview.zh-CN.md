# 面试讲解：截至 2026-09-19

[English](interview.md) | **简体中文**

## 两分钟介绍

我做的是面向 AI API 平台的个人客服原型，尚未接入真实客服。主要处理接入配置、调用异常和常见咨询，重点是如何把历史工单转成有使用边界的知识。

在既往私有数据处理阶段，基于 1,659 条历史案例，我按 13 类问题建立规则分类与质量分层，分流 660 条归档或待复核记录，再结合官方资料做冲突检查，形成 1,086 条带来源和使用限制的检索记录。目前公开项目使用中性名称与 19 条合成资料演示，原始资料另行保管。

系统采用 BM25 与字符相似度检索，通过时效、冲突、错误码和披露规则筛选资料，进入回答、追问或人工核验提示。没有账户与实时工具的场景不生成查询结论。

第一次检查发现了具体问题：401 会被当作 1401 的子串命中，简短错误码更新缺少前一轮产品信息，未解决追问也缺少当前主题。我先固定 48 个合成场景、63 轮对话记录基线，再修复这些机制，并区分通用退款政策与个人退款请求。

在同一套本地规则验收下，完整场景通过数从 39/48 提高到 48/48，多轮任务从 9/14 提高到 14/14；另外 59 项软件测试通过。这只验证已知合成场景中的行为，不能证明真实模型准确率或线上解决率。下一步是人工复核标签、补独立任务样本，再测试真实模型和目标用户体验。

个人贡献请按实际参与情况表达，尤其是业务规则、验收标准、失败判断与取舍；不要把 AI 辅助生成的所有代码都描述成独立手写。

## 数字口径

| 数字 | 解释 |
| --- | --- |
| 660 | 331 条归档／排除 + 329 条待复核，不是人工确认的错误数 |
| 1,086 | 994 条历史摘要 + 92 条官方记录，不是全部当前有效的客户答案 |
| 48/48 | 合成开发回归集满足显式验收规则，不能写成客服准确率 100% |
| 59 | 软件自动化测试数量，API 测试使用模拟响应 |
| 19 条演示资料 | 当前公开项目内的虚构知识；不代表任何公司的政策 |

## 取舍与下一步

- 固定流程便于明确回答边界；没有自主规划、业务工具循环或真实人工工单系统。
- n-gram 是字面相似度，不是 embedding。是否升级检索应由真实问题集验证。
- 引用是生成可见材料列表，不能替代逐论断核查。
- 本地多轮依赖有限规则及最近 8 条消息，复杂省略、否定更正和长对话仍需扩展评测。
- 既往私有快照中的 69 条到期内部来源记录仍待核验；已单独归档，重抽旧文档不能证明政策仍有效。
- 下一轮优先测正确与错误作答的平衡、应升级召回和用户核验耗时。
